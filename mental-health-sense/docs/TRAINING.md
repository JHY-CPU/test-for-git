# GRU 个人基线模型训练详解

> 本文详述系统中 `PersonalBaselineGRU` 的训练方式、样本需求、训练/验证集划分、
> 耗时与算力要求。所有性能数字为在开发机（Intel CPU / Python 3.11 / PyTorch 2.7）
> 上的**实测值**，非估算。相关代码：`src/baseline/trainer.py`、`src/baseline/gru_model.py`。
> 文中对代码的引用一律按**函数名**写（如 `trainer.py::_train_loop`），不用行号——
> 代码重构后行号必漂，按函数名才能定位。

## TL;DR（一句话版）

这是一个**极轻量**（909 参数、两轨模型文件合计约 9.5 KB）的个人基线模型，用**该老人自己的**
过去 7 天特征预测第 8 天。冷启动默认 **35 天数据 → 21 个训练样本 + 7 个留出样本**（建档期可配，见 §7.3），
在 **CPU 上约 0.2 秒**即可训练完成。**没有独立验证集**——这是刻意设计，靠 early-stopping +
权重回滚 + 健康门禁三重机制抑制小样本过拟合（详见第 6 节）。**无需 GPU**，边缘设备
（树莓派 / Jetson）足够。

> **建档期为何是 35 天？** 早期默认 14 天(7 样本)，多种子实验证实其过拟合明显、
> 早期误报偏高；提到 21 天(14 样本)后误报大幅下降、检出率不变（实验数据见 §7.3）。
> v2.1 双轨改造时再提到 **35 天**，有两个新增理由：
> 一是社交轨需覆盖 3 个完整周，否则学不到“周末子女来访”这个正常模式，第一个周末就误报；
> 二是要切得出 7(窗口) + 21(训练) + 7(**留出**) 三段——留出段是 v2.1 新增的、
> 用于估残差统计的必需品（绝不能用训练集残差估阈值，见 §5）。

## 1. GRU 在系统中的定位：异常检测，不是预测

先厘清一个根本点，否则会用错误的标准评价它：

> **GRU 不追求"预测准确"，只需"稳定复现正常态"。**

系统做的是**异常检测**，不是回归预测。GRU 学的是"这位老人正常情况下，今天大概是什么样"。
真正被使用的是**残差**（预测值与实际值之差）：

- 正常日 → 实际值贴近模型学到的常态 → 残差小
- 异常日 → 实际值偏离常态 → 残差大 → 触发后续风险判定

因此哪怕 GRU 对某个特征有**系统性偏差**，只要这个偏差**稳定**（每天都偏同样多），
残差依然稳定，就不会误报。这也是为什么一个只有 909 参数、十几个样本训练出来的模型
能用——它的任务本就不需要大模型的表达力。

> 与此配套的还有 EWMA 动态阈值、连续偏离天数判定、冷启动兜底等（见 `docs/README.md`），
> 本文只聚焦 GRU 本身的训练。

## 2. 模型结构

`src/baseline/gru_model.py::PersonalBaselineGRU`

**★ 双轨：睡眠轨与社交轨各训一个独立模型**，结构相同、维度不同。
两轨不共享权重也不共享 scaler——这正是切断"串味"的关键（见 `docs/VALIDATION.md` 缺陷③）。

```
                睡眠轨 D=8                     社交轨 D=5
输入 (batch, 7, D)          过去 7 天 × 该轨 D 维特征
   │
   ▼
GRU(input=D, hidden=8, layers=1)     → (batch, 7, 8)
   │  取最后时刻隐藏状态
   ▼
Dropout(0.2)                 → (batch, 8)
   │
   ▼
Linear(8 → D)                → (batch, D)    第 8 天的 D 维预测
```

**超参数**（`config/settings.yaml` 的 `gru` 段）：

`gru` 段按轨分块（`gru.sleep` / `gru.social`），`window`/`num_layers`/`dropout` 两轨共用：

| 参数 | 值 | 说明 |
|------|-----|------|
| `feature_dim` | 8 / 5 | 按轨取：睡眠 8 维、社交 5 维（不含时间编码） |
| `hidden_dim` | **8** | 两轨都取 8，刻意取小以防过拟合 |
| `num_layers` | 1 | 单层 GRU |
| `window` | 7 | 用过去 7 天预测第 8 天 |
| `dropout` | 0.2 | 单层时仅作用于 GRU 输出后的 Linear 前 |

**参数量拆解（H=8，与 `train_all_baselines.py` 实测输出核对）：**

| 模块 | 形状 | 睡眠轨 (D=8) | 社交轨 (D=5) |
|------|------|--------------|--------------|
| `gru.weight_ih_l0` | (3H, D) | 192 | 120 |
| `gru.weight_hh_l0` | (3H, H) | 192 | 192 |
| `gru.bias_ih_l0` | (3H,) | 24 | 24 |
| `gru.bias_hh_l0` | (3H,) | 24 | 24 |
| `fc.weight` | (D, H) | 64 | 40 |
| `fc.bias` | (D,) | 8 | 5 |
| **合计** | | **504** | **405** |

> 3H = 24 对应 GRU 的重置门/更新门/候选状态三组权重。
> 两轨合计 **909** 个参数——极小，这是刻意的：单个老人建档期只有 35 天、
> 滑窗后不到 30 个样本，模型必须小到不会把噪声记成规律。

## 3. 训练数据

### 3.1 数据来源与特征

训练数据是**该老人自己的**每日特征向量，从 `data/features/{elder_id}/features_{track}.csv`
读取，只取 `data_quality == "valid"` 的天。两轨特征见
`src/baseline/scaler_utils.py::SLEEP_FEATURES` / `SOCIAL_FEATURES`：

```
睡眠轨(8): sleep_efficiency, waso_min, sol_min, bed_exit_count,
           deep_sleep_ratio, sleep_onset_clock, night_hr_mean, daytime_nap_min
社交轨(5): copresence_min, out_of_home_min, rar_amplitude, rar_iv, activity_counts
```

两轨各有独立的 `features_sleep.csv` / `features_social.csv`，各自独立走
scaler → 滑窗 → 训练 → 留出段统计，互不共享任何中间产物。

### 3.2 样本如何构造：7→1 滑动窗口

原始数据是"每天一行"的时间序列。训练样本通过滑动窗口切分（`trainer.py::_build_windows`）：

```
第 i 个样本：  X = 第 (i-7) ~ (i-1) 天   (7, D)
              y = 第 i 天              (D,)
```

D 为该轨维度：睡眠轨 8、社交轨 5。

所以 **N 天有效数据 → (N − 7) 个训练样本**。这是理解本文所有样本数的关键换算。

### 3.3 训练集 / 验证集划分：**没有独立验证集**（这是刻意设计）

这是全文最容易被误解、也最该讲清楚的一点。

**现状**：冷启动时那 21 个训练样本（默认 35 天建档）**全部用于训练**，代码里没有划出
validation set，也没有 test set（`trainer.py` 里不存在 train/val split）。

**为什么不划验证集？** 三个原因叠加：

1. **样本仍然很少**。冷启动只有 ~21 个训练样本，再切出 3~4 个做验证，训练集只剩 17 个左右——
   验证集小到统计上意义有限，反而让训练更不稳定。
2. **任务是异常检测，不是泛化预测**。传统验证集是为了估计"模型在没见过的数据上
   的泛化误差"。但这里模型的目标是"复现这位老人的正常态"，评价标准是**下游的
   误报率/检出率**，不是留出集上的 MSE。一个在留出集上 MSE 很低的模型，不代表它
   的残差能有效区分正常/异常。
3. **个人基线的特性**。模型是"一人一模型"，数据本就是这个人的完整历史，
   没有"其他样本"可留。

**那靠什么防止过拟合、保证质量？** 用三套替代机制（详见第 6 节）：

| 传统做法 | 本系统的替代 |
|---------|-------------|
| 验证集 early-stopping | **训练损失** early-stopping + 回滚最优权重 |
| 验证集选超参 | 极小模型容量（hidden=8，两轨合计 909 参数）从结构上限制过拟合 |
| 测试集评估泛化 | **系统级验证**：整条链路在真实/仿真数据上的误报率与检出率（见 `docs/VALIDATION.md`） |

> 换句话说：**验证不在"模型"这一层做，而在"系统"这一层做。** 单个 GRU 的好坏，
> 由它喂给下游的残差最终能否正确触发/不触发预警来评判，这才是有意义的验收标准。

## 4. 两种训练模式

系统有两个训练入口，**共用同一套训练循环** `_train_loop`（`trainer.py::_train_loop`）：

| | 冷启动 `train_initial_baseline` | 每周微调 `weekly_retrain` |
|---|---|---|
| 触发时机 | 建档期结束（默认第 35 天），一次性 | 每周日 04:00（`weekly_job`） |
| 数据 | 前 `build_days` 天（默认 35）有效特征 | 最近 30 天有效特征 |
| 样本数 | ~21 | ~23 |
| epochs | 150 | 50 |
| 学习率 | 0.001 | 0.0003（低，防灾难性遗忘） |
| patience | 20 | 10 |
| Scaler | **新拟合**并冻结 | **复用**，绝不重新拟合 |
| 起点 | 随机初始化 | 从上一版 `gru.pth` 继续 |
| 异常天处理 | MAD 健康门禁剔除 | 剔除已判 `is_deviation` 的天 |
| 模型备份 | — | 覆盖前备份为 `gru.prev.pth` |

> **微调为何不能重新拟合 Scaler？** GRU 是在建档期的归一化尺度上学到"正常态"的。
> 若对新数据重新 `fit`，归一化基准会随数据漂移，残差量纲跟着变，异常检测直接失真——
> 今天的偏离可能因为 scaler 被"带偏"而看起来正常。基准必须冻结在建档期
> （`scaler_utils.py::transform_data` 的注释也强调了这点）。

## 5. 冷启动训练流程（7 步详解）

`train_initial_baseline` 的完整步骤（`trainer.py::train_initial_baseline`）：

本节按**双轨**描述，每一轨各跑一遍（`train_all_tracks`）。以睡眠轨为例：

```
1. 读取前 build_days 天有效特征（默认 35）   → (35, 8)   社交轨为 (35, 5)
   ★ 同时剔除含缺测维（NaN）的行——缺 1 维时质量仍判 valid，
     而 NaN 进 StandardScaler.fit 会让归一化基准整体报废
2. 健康门禁：MAD 逐特征离群筛查              → 剔除异常天（占比>50% 则拒绝建档）
3. 拟合 StandardScaler 并冻结                → scaler_{track}.pkl
4. 切分：训练目标日 [7, 28)，留出目标日 [28, 35)
   35 天 = 7（喂窗口）+ 21（训练序列）+ 7（留出序列）
5. 训练 GRU，只用训练段（150 epoch，early-stop + 回滚最优权重）
                                             → gru_{track}.pth
6. ★ 在**留出段**上估残差统计（signed + abs 两套）
                                             → residual_stats_{track}.pkl
7. 初始化 EWMA 累积基线（社交轨按 is_weekend 分池）
                                             → ewma_{track}*.pkl + baseline_meta.json
```

**几个关键点：**

- **第 2 步（健康门禁）先于拟合 Scaler**：这样归一化基准不会被异常天带偏。
- **★ 第 6 步必须用留出段，绝不能用训练集**。这是本项目最重要的一条不变量，
  它切断的是一条闭合的误报链：

  ```
  模型对训练集的残差被压得极小
    → residual_stats["std"] 趋零
    → signed_z = residual / std 的分母趋零
    → 任何微小偏差被放大成巨大 z 分
    → 建档期一过就疯狂误报
  ```

  留出段是模型训练时没见过的日子，它的残差尺度才反映真实预测误差。
  `baseline_meta.json` 里的 `threshold_source` 会记为 `"holdout"`。

- **两套残差统计各自独立**：`signed = observed − predicted`（判方向），
  `abs = |signed|`（打幅度分）。只留 abs 会让方向信息在进 rules.py 之前就丢失，
  所有 down 方向规则失效；用 abs 的 std 去标准化 signed 残差则是量纲错配。
- **第 7 步（EWMA 预热）会记录 `ewma_n_at_train`**：建档期的 28 个样本已经把 EWMA
  的样本数顶到 28，观察期判定必须用"训练后新增的推理天数"（`ewma.n − ewma_n_at_train`），
  否则观察期会瞬间耗尽、形同虚设。

**产出文件**（按轨后缀，两轨共 12 个文件，实测合计约 13 KB）：

| 文件 | 内容 |
|------|------|
| `gru_sleep.pth` / `gru_social.pth` | GRU 权重（504 / 405 参数） |
| `scaler_sleep.pkl` / `scaler_social.pkl` | StandardScaler（归一化基准，永久冻结） |
| `residual_stats_sleep.pkl` / `residual_stats_social.pkl` | **留出段**残差统计（signed + abs） |
| `ewma_sleep.pkl` | 睡眠轨 EWMA 池（单池） |
| `ewma_social_weekday.pkl` / `ewma_social_weekend.pkl` | 社交轨 EWMA 池（分池） |
| `ewma_*_state.pkl` | 冻结计数与 last_day_key |
| `baseline_meta.json` | 两轨共用，按 track 分键；含 `threshold_source: "holdout"` |

## 6. 过拟合抑制：21 个样本训练 909 参数（双轨合计），怎么不炸？

参数量（909）远大于样本量（~21），这是典型的过拟合温床（14 天/7 样本的时代更严重，
正是建档期提到 35 天的原因，见 §7.3）。系统用**四层机制**压制：

### 6.1 early-stopping + 回滚最优权重（`_train_loop`）

连续 `patience` 轮训练损失无改善则提前停止，并把权重**回滚到最优点**（不是停在
抖动的高点）。冷启动 patience=20、微调 patience=10。这是替代"验证集 early-stopping"
的核心手段。

> **一个易错细节**：最优权重必须在**梯度更新之前**保存。代码里先按"产生当前 loss 的
> 这组权重"记录 `best_state`，再 `optimizer.step()`——否则存下的是更新一步之后的权重，
> 与刚记录的 `best_loss` 差一个梯度步，回滚点会偏移（`trainer.py::_train_loop` 的
> best_state 保存处，这是修过的 off-by-one）。

### 6.2 极小模型容量

`hidden_dim=8`、`num_layers=1`。从**结构上**限制表达力——模型小到学不出复杂的
过拟合模式。这也是为什么没有验证集也相对安全。

### 6.3 数据健康门禁（防"学坏"）

建档期若混入异常态，GRU 会把异常学成"正常基线"，之后再也报不出来。训练前用
**MAD（中位数绝对偏差）** 逐特征离群筛查（`data_health.py`）：

- 个别离群天 → 剔除后训练；
- 离群天占比 > 50% → 拒绝建档，提示顺延。

MAD 相比"均值 ± Nσ"对离群点本身不敏感，适合"样本少、又要判断哪几天离群"的场景。

### 6.4 微调防污染 + 低学习率

微调只用 `is_deviation=False` 的正常天（排除已判偏离的日期），且用低学习率 0.0003
防灾难性遗忘。正常天不足 10 天（`window+3`）则跳过微调，而非用脏数据。

## 7. 样本需求与训练耗时（实测）

### 7.1 样本量需求

| 场景 | 最少有效天数 | 训练样本数 | 说明 |
|------|-------------|-----------|------|
| 冷启动建档 | **35 天**（默认，可配） | 21 | 低于 `build_days` 天抛错等待 |
| 健康门禁剔除后 | **10 天** | ≥ 1 | 剔除离群后不足 `window+1+2`(10) 天（训练段≥1 样本 + 留出段≥2 天）则拒绝建档 |
| 每周微调 | **10 天** | ≥ 3 | 独立门槛（`window+3`），与建档期无关；低于 10 天跳过微调 |
| 微调（满 30 天） | 30 天 | ~23 | 默认 `recent_days=30` |

> **建档期为何不是 8 天？** 构造 1 个样本理论上只要 8 天，但样本越少过拟合越重
> （见 §7.3 实验）；35 天(21 训练样本 + 7 留出样本)是"误报低 + 检出不变 + 不纳入过期数据"的甜点，
> 也给健康门禁留出剔除离群天的余量。`build_days` 可在 `config/settings.yaml` 调整。

### 7.2 训练耗时（开发机 CPU 实测）

环境：Intel CPU、Python 3.11.9、PyTorch 2.7.1、全程 **CPU**（模型太小，用 GPU 反因
数据搬运更慢）。

| 场景 | 耗时 | 备注 |
|------|------|------|
| 冷启动（35 天/21 样本真实数据，触发 early-stop） | **~0.22 秒** | 稳态多次测量 210~235 ms |
| 冷启动首次（含 import/JIT 预热） | ~2.0 秒 | 仅进程首跑一次 |
| 每周微调（~23 样本，50 轮） | **~0.06 秒** | |
| 单次推理（预测一天） | **~0.15 毫秒** | 1000 次平均 |

> 建档期从 14 天(7 样本)提到 21 天(14 样本)后，冷启动耗时由 ~0.18 秒略增到 ~0.22 秒，
> 量级不变，仍是亚秒级。early-stopping 让模型在真实数据上很快收敛，不需要跑满 150 轮。

### 7.3 建档期为什么不能太短：多种子对比实验（历史记录）

> ⚠️ 本节“默认取 21 天”的结论**已被 v2.1 超越**（现为 35 天，理由见 §5 与本节末尾）。
> 实验数据与“样本越少过拟合越重”这个结论仍然成立，故整节保留备查。

当年把默认建档期从 14 天调整为 21 天，是基于一次受控实验的决定，而非拍脑袋。

**方法**：仿真数据，20 个随机种子打破 n=1；对每个建档窗口用真实 `_train_loop` 训练，
用真实的 `static_threshold = 加权(residual_mean) + 2.5×加权(residual_std)` 单天判定。
评测集对所有窗口相同：正常留出 day38–50（测误报率 FPR），异常 day25–30（测检出率）。
为隔离"样本数量"这一单一变量，本实验关闭了健康门禁。

**结果**（20 种子均值）：

| 建档窗口 | 样本 | 过拟合 gap | 静态阈值 | 单天 FPR | 检出率 |
|---------|------|-----------|---------|---------|--------|
| 14 天 | 7 | 0.53 | 1.185 | **26.5%** | 100% |
| 18 天 | 11 | 0.42 | 1.499 | 3.1% | 100% |
| **21 天** | **14** | **0.36** | **1.625** | **1.5%** | **100%** |
| 24 天 | 17 | 0.32 | 1.698 | 0% | 100% |
| 28 天 | 21 | 0.14 | 1.726 | 0% | **0.8%** ⚠️ |

> "过拟合 gap" = 留出正常残差 − 训练残差，越大越过拟合。

**三条结论**：
1. **过拟合真实存在**：14 天时训练残差(0.46)仅为留出残差(0.99)的一半，模型在"背题"。
   gap 随样本数单调下降。
2. **改善建档期收益陡峭**：14→18 天 FPR 从 26.5% 断崖降到 3.1%，21 天 1.5%，检出率全程 100%。
3. **不能盲目加大**：28 天检出率崩到 0.8%，因其建档区间吃进了异常期 day25–28，把异常
   学成了正常基线——正是健康门禁要防的情形。故存在"纳入异常/过期数据"的上界风险。

**当年为何选 21 而非 24**：21 天已拿到绝大部分收益（gap 减 1/3、FPR 进入 ~1%），检出满分，
又离"异常污染窗口"的风险有安全距离。

**重要 caveat**（避免高估）：
- 这是"单天 + 仅静态阈值"的最裸判定。真实系统还有观察期 + EWMA 动态阈值 + 连续天数
  门槛，会进一步压低 FPR。故 26.5% 不代表真实系统 14 天窗口真会天天误报——但更小的
  gap 意味着 `residual_stats` 更可信、EWMA 冷启动更稳，是**从源头改善基线质量**。
- 仿真是"循环论证"的（正常天纯高斯、无周节律）。同一数据上的**相对趋势**可信，
  **绝对 FPR 值**待真实数据校准（见 `docs/VALIDATION.md` 对仿真局限的讨论）。
- 代价：建档期 14→21 天多等 7 天盲区，由冷启动兜底顶着。
- **v2.1 后续**：为切出留出段并覆盖社交轨的 3 个完整周，建档期再提到 35 天，
  盲区同样由冷启动兜底覆盖。

## 8. 算力要求

### 8.1 GRU 本身：几乎无门槛

| 维度 | 要求 | 说明 |
|------|------|------|
| **GPU** | **不需要** | 909 参数、7~23 样本，CPU 亚秒级完成 |
| **CPU** | 任意现代 CPU | 单核足够；ARM（树莓派）也可 |
| **训练内存峰值** | < 100 MB | 主要是 PyTorch 运行时本身 |
| **推理内存** | < 50 MB | 单次前向，几乎可忽略 |
| **磁盘** | 每位老人约 13 KB | 12 个基线文件合计（不含微调前的 `.prev` 备份） |
| **PyTorch** | CPU 版即可 | 无需 CUDA 版 |

一句话：**GRU 这条线对硬件没有任何实质门槛**。一整天全部老人的训练 + 推理，
一颗普通 CPU 核心轻松搞定。

### 8.2 全系统算力：CPU 即可，不再有语音大模型这条线

> **变更说明（2026-07-29）**：随"移除抑郁判断 + SenseVoice 声学子系统（10→6 维）"，
> 原来那条数亿参数、需要 GPU 的实时语音情感识别（SenseVoice）线**已整体删除**，不再是
> 本系统的一部分。历史上曾把它列为"真正吃算力的大头"，该前提现已不成立。

现在系统里唯一的模型就是 GRU 每日轨（本文主题）。社交轨特征来自 C6c 边缘侧人形检测
（`copresence_min`）与 T1C 人体移动传感器事件（`out_of_home_min` / `rar_amplitude` /
`rar_iv` / `activity_counts`），是轻量的统计聚合，无任何语音/声学处理，算力可忽略。

| 组件 | 算力需求 | 设备建议 |
|------|---------|---------|
| **GRU 每日轨**（本文主题） | 极低，CPU 即可 | 任意设备 |
| **特征聚合**（人形检测 + 传感器事件统计） | 极低，CPU 即可 | 任意设备 |

**部署结论：** 全系统（GRU + EWMA + 特征聚合）在树莓派 5 甚至更低端设备上即可运行，
无需 GPU。

## 9. 常见问题（FAQ）

**Q：十几个样本训练一个模型，靠谱吗？**
A：因为任务是"复现正常态"而非复杂预测，配合极小容量（909 参数）+ early-stopping +
健康门禁，~21 个样本（35 天建档）足以拟合出一个稳定的个人基线。评判标准是下游残差能否正确
触发/不触发预警，不是模型本身的 MSE。建档期取 35 天(21 训练样本)而非更少，正是实验
证明样本太少会过拟合、误报偏高（§7.3）。

**Q：没有验证集，怎么知道模型没坏？**
A：验证在**系统层**做——端到端冒烟测试 + 消融实验（`docs/VALIDATION.md`），看整条
链路的误报率/检出率。模型层则靠 early-stopping、极小容量、健康门禁三重保险。

**Q：建档期不足（默认 35 天）怎么办？**
A：`train_initial_baseline` 抛错等待数据积累。此期间由**冷启动兜底**
（`cold_start_fallback.py`，滑动均值 ± 3σ）提供基础检测，消除头两周盲区。

**Q：微调把模型搞坏了能回滚吗？**
A：能。每次微调覆盖 `gru.pth` 前先备份为 `gru.prev.pth`，可手动回滚。

**Q：为什么每位老人都要单独训练？**
A："一人一模型"是本系统的核心设计——"自己和自己比"，避免用群体平均误判个体差异。
但单次训练仅 ~0.2 秒，成本可忽略。

**Q：能用 GPU 加速训练吗？**
A：可以强制用，但**更慢**。模型太小，数据在 CPU↔GPU 间搬运的开销远大于计算本身。
CPU 是这个规模模型的最优选择。
