# 系统验证方案

> 在真实传感器设备尚未到位、无真实老人数据接入的前提下，如何验证本系统的
> 正确性、设计合理性与真实有效性。

## 0. 先分清"验证"到底在验证什么

"这个系统到底有没有用"其实混了三个层次不同的问题，它们各自能被验证到什么程度
完全不一样。混在一起谈，就会陷入"模拟数据自说自话"或"没数据什么都做不了"两种误区。

| 层次 | 在回答的问题 | 无真实数据能验证吗 | 证据强度 |
|------|-------------|-------------------|---------|
| **A. 代码对不对** | 算法有没有被正确实现 | ✅ 现在就能 | 基础 |
| **B. 设计好不好** | 本方法是否优于替代方案（群体阈值 / 单日触发等） | ✅ 现在就能 | 中 |
| **C. 真的有用吗** | 能否测出一个真实老人的心理下滑 | ❌ 必须真实数据 + 临床金标准 | 高 |

**核心诚实判断**：C 这一层，靠模拟数据永远无法回答，再精细的仿真也不行。这不是本
系统的缺陷，而是所有非接触式心理感知系统的共同天花板。本项目 README 已如实声明
"特征选择有据，特征测量精度需实测"——这个定位是准确的，不应回避。

但 A 和 B 现在就能扎实验证，且正是竞赛评审、论文、答辩真正考察的核心。因此本方案
的策略是：**把 A、B 做到无可挑剔，把 C 用公开数据集和小试点尽可能往前推，并对 C 的
局限保持透明。**

---

## 1. 三层验证框架总览

```
证据强度  弱 ─────────────────────────────────────────────► 强

层次 A  ┌─ 单元测试（已有 133 个）
（代码）└─ 端到端链路冒烟测试（daily_job 单入口 + 统一系统生产链路）

层次 B  ┌─ 非循环仿真（打破"按答案出题"）
（设计）├─ 8 项消融实验
        └─ 敏感性分析（参数扰动）

层次 C  ┌─ 公开真实数据集验证（Depresjon / NSRR）
（有效）└─ 真实设备纵向验证（设备到位后）
```

每一层都能独立产出成果，且证据一层比一层硬。建议按 A → B → C 顺序推进。

## 2. 层次 A：验证代码正确性（现在就能做）

**目标**：证明算法被正确实现，数据流从传感器输入到预警输出全链路无断点。
**回答的不是"有没有用"，而是"有没有 bug"**——这是后续一切验证的地基。

### 2.1 单元测试（已具备）

当前 `tests/` 下 475 个用例覆盖聚合、填充、GRU、EWMA（含偏离日冻结）、健康门禁、
风险规则与判定（含方向闸门）、
指标计算、实时↔每日衔接（自然日聚合 / 墙上时钟窗口 / 缺失标记）、训练循环 early-stopping 等。运行：

```bash
pytest tests/ -v
```

**验收标准**：全部通过；关键判定分支（方向匹配、连续天数、幅度门槛、观察期）
有对应回归用例。

### 2.2 端到端链路冒烟测试

证明"三路传感器 JSON → 双轨特征（睡眠 8 维 / 社交 5 维）→ 各轨 GRU 残差 →
EWMA 阈值 → 风险分类 → 预警"
整条链路能跑通、各环节数据形状与状态流转正确。

```bash
python scripts/generate_simulation_data.py   # 造数据
python scripts/train_all_baselines.py         # 冷启动训练
python scripts/run_daily_pipeline.py --date <注入异常期内某天>
python scripts/health_check.py                # 完整性检查
```

**验收标准**：注入异常期内能产出非零 anomaly_score 并逐级升级；正常期不误报；
`daily_inference/*.json` 字段完整、status 流转符合预期（cold_start → observation → success）。

> **入口覆盖说明**：`run_daily_pipeline`（`daily_job`）是完整实现的每日入口，上面命令走的就是它。
> `UnifiedScheduler`（统一系统生产链路）此前的每日推理是 TODO 桩，冒烟只覆盖 `daily_job` 单入口；
> 现已打通——统一调度器真正调用同一个 `run_daily_pipeline`，三路传感器数据统一取自 `data/raw/`。
> 因此层次 A 的冒烟结论现已覆盖"统一系统"这条生产链路（详见 `docs/TODO.md` P0）。

> ⚠️ **重要认知**：层次 A 全过 **不代表系统有用**。它只证明"我设计的逻辑被正确执行了"，
> 不证明"这个逻辑能识别真实的心理下滑"。不要把 A 的绿灯误读成 C 的结论。

## 3. 层次 B：验证设计合理性（现在就能做，是当前重点）

**目标**：证明本系统的关键设计选择（个人化基线、EWMA 动态阈值、连续趋势判定、
健康门禁等）确实优于朴素替代方案。这是无真实数据条件下**能产出的最硬证据**，
也是论文/答辩的主体。

### 3.1 前提：先把仿真改成"非循环"的（关键）

**当前仿真的致命问题**：`generate_simulation_data.py` 注入的异常方向
（睡眠恶化：sleep_efficiency↓ + deep_sleep_ratio↓ + sfi↑ + hrv_rmssd↓）**与 `rules.py`
要检测的方向完全一致**。等于"按检测器的标准答案出题，再拿去考检测器"，必然检出。
这只能证明链路通（属层次 A），**证明不了判别能力**。

要让仿真具备验证价值，必须打破循环：

1. **正常日注入真实自然波动**：老人本就有安静的一天、偶尔睡不好的一天。正常日
   必须带真实噪声，"误报率"才是可测量的真数字，而非恒为 0 的摆设。
2. **异常注入多样化**：除了当前的"典型全特征异常"，增加
   - 渐变型（特征缓慢漂移，考验提前预警能力）
   - 部分型（只有 2/6 个特征异常，考验方向匹配的鲁棒性）
   - 模糊型（幅度只在阈值附近擦线，考验幅度门槛）
3. **加入混淆项（negative hard cases）**：
   - "周末所以话少" → 应 **不** 报社交孤独
   - "感冒导致睡眠差" → 应判 **睡眠问题**、**不** 应误报社交孤独
   - 单日剧烈波动后恢复 → 应 **不** 升级到提醒/严重

**能扛住混淆项而不误报的系统，才配称"经过验证"。**

### 3.2 消融实验矩阵

在同一份（改造后的）仿真数据上，逐一关闭某个设计再对比指标。README 已列 8 项：

| # | 变量 | 对比对象 | 预期结论 | 关键指标 |
|---|------|---------|---------|---------|
| 1 | 个人基线 vs 群体阈值 | 换成群体固定阈值 | 误报率低 4–6× | FPR |
| 2 | EWMA vs 固定 60 天窗口 | 换成滑动窗口 | EWMA 更早稳定 | 阈值收敛天数 |
| 3 | GRU vs 移动平均 | 换成 MA 预测 | GRU 提前 1–2 天 | 提前预警天数 |
| 4 | 含社交 vs 仅生理特征 | 去掉社交特征 | 检出率 +20% | Recall |
| 5 | 连续 N=3 vs N=1 | 单日即触发 | 误报率 3.2→0.4/天 | 每日误报次数 |
| 6 | 有无健康门禁 | 建档期注入异常 | 门禁避免"学坏"漏报 | 漏报率 |
| 7 | 有无 early-stopping | 关掉提前停止 | 抑制过拟合，残差更稳 | 验证残差方差 |
| 8 | 有无冷启动兜底 | 关掉兜底 | 消除建档期盲区 | 盲区天数 |

**产出**：每项一张对比表 + 一句结论。这是 B 层的核心交付物。

### 3.3 敏感性分析

对关键超参（`alpha`、`sigma_multiplier`、`consecutive` 阈值、`threshold_ratio`）
做网格扰动，画出"参数 → FPR/Recall"曲线。

**目的**：证明系统表现不是靠某一组恰好调好的魔法参数，在合理范围内稳健。
这直接回应评审最常见的质疑——"你这结果是不是调参调出来的？"

## 4. 层次 C：验证真实有效性（部分现在能做）

**目标**：回答"能否测出真实的心理下滑"。完整的 C 需要真实设备 + 临床金标准，
但**无需自有设备也能推进一大步**——用公开真实数据集。

### 4.1 公开真实数据集验证（无设备条件下最强证据）

不需要自己的雷达/拾音器，也能拿到**真实信号 + 真实临床标签**，验证"单个特征 →
心理状态"这条映射链在真人身上到底成不成立。

| 数据集 | 内容 | 验证本系统的哪部分 | 备注 |
|--------|------|-------------------|------|
| **Depresjon** | 体动记录(actigraphy) + MADRS 抑郁评分 | `activity_counts` / `rar_*` 特征、个人纵向基线思路 | 最贴合，优先 |
| **NSRR（MESA/SHHS）** | PSG 多导睡眠 | 睡眠特征（效率、深睡、SFI、HRV）的临床效度 | 验证睡眠链 |

**建议动作**：先接 **Depresjon**——它几乎正好对应社交轨的 `activity_counts` 与
`rar_amplitude`/`rar_iv`，且带真实临床
分级（MADRS）可作金标准，可直接检验"个人化基线偏离"思路在真人纵向数据上是否比
群体阈值更早、更准地捕捉到活动量的异常下滑。

> ⚠️ 使用前须确认各数据集的授权协议与伦理要求，部分需申请。查询获取方式时不要
> 提交任何隐私/凭据信息。

### 4.2 真实设备纵向验证（设备到位后）

完整的 C 只有在此阶段才谈得上：
- **测量效度**：雷达估算的 RMSSD/深睡分期 vs PSG 金标准的一致性
- **真实误报率**：真实老人正常生活下，系统每天误报几次
- **纵向敏感度**：真实状态变化发生时，系统能否、提前多久捕捉到
- 需配合定期的标准量表作为参照标签（GDS 老年抑郁量表属外部专用抑郁模型的参照，
  不属本双轨特征集）

## 6. 汇报/答辩时的诚实措辞建议

- ✅ 可以说："在受控仿真与消融实验中，个人化基线相比群体阈值将误报率降低 N×"
  （B 层，站得住）
- ✅ 可以说："在 Depresjon 真实数据上，个人基线偏离与 MADRS 评分变化的相关性为……"
  （C 层初步，站得住）
- ❌ 不要说："本系统能准确诊断疾病（如老年抑郁）"——这是临床诊断声明，本系统刻意
  回避，且无任何数据支撑；抑郁风险由外部专用模型承担，不在本双轨特征集范围内。
- ✅ 应主动声明局限："特征选择有文献依据；特征的测量效度与真实场景误报率
  需真实设备验证，为后续工作。"

**主动暴露局限不会削弱工作，反而体现科学严谨——评审反感的是把仿真结果包装成
临床结论，而非承认边界。**

## 7. 实际执行记录（合成数据验证）

开发验证阶段无 21 天真实数据，故用合成数据落地了阶段 1→2。两个脚本：

- `scripts/validate_synthetic.py`（**范围 1：跑通**，层次 A）
- `scripts/validate_discriminative.py`（**范围 2：判别力**，层次 B）

均用独立 elder_id、跑完自清，不碰真实老人数据。

### 7.1 范围 1：端到端跑通（层次 A）——通过

造 60 天数据（建档 1-35 / 正常 36-39 / **睡眠异常 40-46** / 恢复 47-49 /
**社交异常 50-58** / 恢复 59-60），逐日走真实每日管道 + 建档期训练。
两段异常**错开**是为了验证双轨的信号隔离。当前 **19/19 全过**：

- 链路 60/60 天无崩溃；建档期 35 天走稳健兜底（无监测盲区）；
- 状态流转正确：`cold_start_fallback` → `success`(day36+)，观察期已取消；
- 两段异常各自升到 Level 3、尾期回落 ≤Level 1；
- ★ 信号隔离：睡眠异常期社交轨误报 0 天、社交异常期睡眠轨误报 1 天（均容许 ≤1）。

> **容差为什么不是 0**：正常天带 AR(1) 噪声，单轨单日擦线越阈本就会偶发
> （day54 是 score 1.45 / 阈值 1.29，前后各天 0.67~1.17，无趋势——噪声不是串味）。
> 要求恒为 0 等于要求零误报率，只能靠抬高阈值换取，代价是真异常也漏。
> 真正的串味会表现为连续多天同向抬升，"≤1 天"能区分开。

> **⚠ 此前记录的"通过"有假绿成分**：`validate_synthetic.py` 长期只固定了
> 数据种子（777），**没固定 torch 随机种子**。两轨 GRU 的随机初始化不受数据
> 种子影响，而建档期仅 35 天样本、模型又刻意取小，初值差异足以让"擦线"场景
> 在两次运行间翻转（实测 `social_decline` 激活与否会飘）。已补
> `torch.manual_seed`，与 `validate_discriminative.py` 同一处理，现连跑两次
> 结果一致。**教训**：验证脚本自身的可复现性要和被验证代码一样对待——
> 不可复现的绿色比红色更危险，因为它会让人停止追查。

**证明**：统一每日链路端到端可跑、状态机正确、双轨信号隔离成立。**不证明**判别力。

### 7.2 范围 2：判别力（层次 B）——进行中，已暴露两个真实问题

正常天改用**真实噪声**（AR(1) 自相关 + 周末效应），并加**混淆项**（单日尖峰 / 短期
社交低落 / 睡眠全面好转），共 10 个场景（5 真阳 + 4 混淆 + 1 已知漏报），
打破了范围 1 的"循环论证"。

**当前状态（v2.1 双轨）：9/9 通过**（KM 场景不计分）。
运行 `python scripts/validate_discriminative.py`。

| 类 | 场景 | 考察点 |
|----|------|--------|
| TP | `TP_sleep` | 睡眠稳定性恶化：效率↓ + WASO↑ + 离床↑ |
| TP | `TP_sleep_minimal` | 只中两个必选维 → 应检出但**不**激活类型 |
| TP | `TP_sleep_drift` | 10 天渐变漂移（趋势捕捉，非阶跃） |
| TP | `TP_social` | 社会连接减弱：共处↓ + 外出↓ + 活动↓ |
| TP | `TP_circadian` | 节律紊乱：RA↓ + IV↑ + 相位漂移 |
| TN | `TN_all_normal` | 基础误报率 |
| TN | `TN_single_spike` | 单日尖峰不该升级 |
| TN | `TN_short_social` | 4 天 < 滚动窗门槛，不该报 |
| TN | `TN_sleep_improved` | **方向闸门**：全面好转不该报警 |
| KM | `KM_social_partial` | 只共处↓、外出照常 → 已知漏报 |

★ v2.1 双轨从**结构上**切断了 v2.0 的主要串味源（两轨各自独立的 GRU 与 scaler），
故 TP 场景现在**同时**断言"应报的类型报了"与"另一轨保持安静"——这是 v2.0 做不到的。

范围 1/2 先后逼出五个此前未知的真实缺陷，其中三个（④⑤⑥）是本轮双轨重构后新发现的：

**缺陷① 风险类型永不激活（已修复）**
`daily_inference` 存日志时不含 `risk_types`，而连续天数统计从日志读它 → 恒为 0 →
类型激活条件（连续≥3/5 天）永不满足。表现：风险**等级**能升到 Level 3，但**永远
报不出**"是睡眠/社交哪一种"。
修复：`rules.py`/`judge.py` 解耦"当天达标(qualifies)"与"连续激活"，把 qualifies
写回日志供次日统计。修复后睡眠恶化注入场景在第 3 个连续日正确激活"睡眠问题"。

**缺陷② 风险类型误激活（已部分修复）**
类型判定用固定门槛 `final_score>1.0`，不受动态阈值保护，正常数据上 |z| 常在 1 附近
→ 频繁误达标 → 攒够连续天数后各类型全误报（诊断证实：纯高斯正常数据也全线误报，
非噪声过猛所致）。
部分修复：类型激活挂靠"当天整体已判偏离(`is_deviation`)"——正常日不再分类。
修复后范围 2 稳定通过 6/8（脚本已固定随机种子——数据生成 hashlib + 训练
torch.manual_seed，保证结果可复现；此前用内置 hash() 未固定，通过数在 4~6/8 飘）。
剩余 2 个失败仍是缺陷③"串味"类：正常数据偶误报睡眠、感冒场景过度升级。

**缺陷③ 跨类型"串味"（维度重叠主因已消除，残余待复验）——成因分析（三个原因）**

> 以下小节记录 **v2.0（单轨 6 维）** 时期的诊断过程。
> 文中的 `sad_ratio` / `social_turns` / `daily_activity` / `depression` 规则**均已删除**，
> 保留叙述是为了说明缺陷是怎么定位的、以及双轨拆分解决了什么。

经受控实验分离，"串味"并非单一原因，而是三者叠加，其中**维度重叠曾是主因**。
本次特征精简（10→6 维，删除 4 个声学维度与 `depression` 规则）已从根本上消除该主因，
仅余两个次要成因待复验：

| 原因 | 属于 | 状态 | 说明 |
|------|------|------|------|
| A. 共享 GRU 外溢 | 架构 | 残余（中，残差 ~1–2） | 一个 GRU 联合预测 6 维，某维异常极端时共享隐藏状态被带偏，其他维残差虚高（重构前实测量级 \|1.0\|~\|2.1\|） |
| **B. 维度重叠** | **维度设计** | **✅ 已消除（本次重构）** | 曾是压倒性主因（残差曾飙到 +8.7）：`sad_ratio` 同时进入 `depression` 与 `social_isolation` 两条规则。现 `sad_ratio` 与 `depression` 规则均删除、`social_isolation` 改为仅看 `social_turns`/`daily_activity` 下降，重叠通道消失 |
| C. 打分门槛松 | 判定逻辑 | 残余（放大 A） | 激活只需"≥1 特征方向达标 + 加权分>1.0"，仍可能被单个外溢残差拉过线 |

**原因 A（共享 GRU 外溢，残余）**：一个 GRU 联合预测 6 维，某维异常极端时共享隐藏状态被带偏，
其他维预测随之偏离、残差虚高。是共享模型的固有取舍（换来跨维关联学习，见 `docs/TRAINING.md`）。
特征精简不改变这一机制，仍需在类型判定层防范。

**原因 B（维度重叠，曾是主因，已消除）**：曾经 `sad_ratio` 同时进入 `depression` 与
`social_isolation` 两条规则，异常时 sad_ratio 残差飙到 +8.7，单枪匹马把 social_isolation 的
加权分拉过线——即便社交自身核心特征 `social_turns` 残差仅 +0.14（人根本没社交孤独）。
**本次重构删除了 `sad_ratio`、删除了 `depression` 风险规则，`social_isolation` 改为仅依据
`social_turns`↓ + `daily_activity`↓，这条跨类型重叠通道从根本上消失，主因已消除。**

**原因 C（打分松，残余）**：`classify_risk_type` 激活条件仅需 `len(exceeding)>=1 and final_score>1.0`，
"只需 1 个特征"的宽松门槛在主因 B 消除后仍可能被原因 A 的外溢残差拉过线，需一并收紧。

**修复进展（v2.1 双轨）**：原因 B（维度重叠）已随特征精简消除；原因 A（共享 GRU 外溢）
已由**双轨拆分**从结构上解决——睡眠 8 维与社交 5 维各有独立的 GRU 与 scaler，
睡眠残差不再经隐藏状态耦合进社交预测。原因 C 由"必选维 + 可选池"的规则结构收紧
（详见 `src/risk/rules.py`）。

**缺陷④ EWMA 学会异常，把持续性异常掩盖掉（本轮新发现，已修复）**

自适应基线的经典失效模式。EWMA 每天都把当天的异常分喂进基线，**包括异常日**。
于是基线在两三天内"学会"这次异常，阈值随分数一起抬高，持续性异常被自己的历史掩盖：
偏离标志开始闪烁，永远凑不满"连续 N 天"，等级卡在 L1。

实测（`TP_social`，共处归零、连续 11 天）：

| 天 | 异常分 | 阈值 | 判偏离 |
|----|--------|------|--------|
| d40 | 2.40 | 1.37 | Y |
| d41 | 1.93 | 1.94 | **.** |
| d42 | 2.21 | 2.02 | Y |
| d43 | 1.78 | 2.02 | **.** |
| d44–d50 | 1.41~1.76 | 2.02 | 几乎全 . |

阈值 1.37 → 1.94 → 2.02 一路追平分数，11 天里只有 5 天被判偏离且不连续，等级 L1。
一次**共处时间归零持续 11 天**的社交崩塌，系统只报"关注"。

修复：`TrackEWMAPools.update()` 增加 `is_deviation` 参数，**偏离日冻结基线更新**。
但冻结不能无限——老人若真的永久性衰退（搬家后再没人来访），基线该重新学习，
否则会永久报警、家属很快脱敏。故设 `max_freeze_days=14`：连续冻结满两周后强制恢复更新，
此时该报的风险早已报过，重新基线化是为了让系统对**下一次**变化仍然敏感。
`freeze_streak` 需随基线落盘（`ewma_<track>_state.pkl`）——每天是独立进程，
不持久化的话计数每天从 0 起算，冻结上限永远触发不到。

修复后 `TP_social`：社交轨偏离 5 天 → **16 天**，等级 L1 → **L3**。

**缺陷⑤ 好转被判成"严重风险"（缺陷④修复后暴露，已修复）**

`anomaly_score` 用的是 **abs** 残差，方向无关——"睡眠效率从 0.88 涨到 0.97"与
"掉到 0.68"产生同样大的分数。缺陷④修复后持续偏离不再被掩盖，这个问题立刻显形：
`TN_sleep_improved`（睡眠全面变好）等级 L1 → **L3**。家属会收到一条
"您父亲睡眠严重异常"，而实情是老人睡得更好了。这类误报对信任的破坏比漏报更快。

风险类型规则本身是有方向的（读 `signed_z`），确实一个类型都没激活；
但**等级**不看类型，照样升到 L3。

修复：`judge.py` 增加**方向闸门**（`_has_adverse_movement`）。L2/L3 会触发家属提醒/
网格员介入，代价高，故要求有"朝坏方向"的正面证据；若驱动升级的那段连续偏离**全是好转**，
封顶在 L1"关注"（变化本身值得留意——可能是躁狂期、也可能是数据问题——但不该发风险提醒）。

三个细节都是被实测逼出来的，不是设计时想到的：

1. **数据缺失不算好转的证据**。`signed_z` 为空或 `signed_available=False` 时保留原等级。
   否则拿不到方向信息就会静默降级真实风险。
2. **`direction="any"` 的维门槛要更高（2σ 而非 1σ）**。`sleep_onset_clock` 不含好/坏信息，
   1.3σ 的就寝时间抖动是正常生活波动；按 1σ 计入"变坏的证据"，闸门几乎永远放行。
3. **只看驱动升级的那段连续偏离，且要求过半天数朝坏方向**。用整个 7 天窗会被一天过渡期
   的混合信号翻掉；而"任一天朝坏方向就放行"同样太松——实测一周全面好转中夹一天
   `sleep_onset_clock` 2.26σ 的抖动就能放行 L3。升级本身是"持续偏离"换来的，
   方向证据也该持续。

修复后 `TN_sleep_improved` 回到 L1，范围 2 达到 9/9。

**缺陷⑥ 单维门槛对变异系数不同的维不是同一件事（补 torch 种子后暴露，已修复）**

给 `validate_synthetic.py` 补上 `torch.manual_seed` 之后，范围 1 从"19/19"变成
稳定的 18/19——失败项是**社会类型激活为空**。也就是说：一次
**共处从 57 分钟归零到 6 分钟、持续 9 天**的社交崩塌，等级升到了 L3，
却报不出"社会连接减弱"这个类型。家属只会看到"严重风险"，看不到是哪一类。

诊断（`social_decline` 三个必选维的实测 `signed_z`）：

| 维 | 变异系数 | 原始跌幅 | 退缩期 z | 过 1.2 门槛？ |
|----|---------|---------|---------|--------------|
| `activity_counts` | ≈13%（185±25） | ~2.6× | −3.1 ~ −4.1 | 稳定过 |
| `out_of_home_min` | ≈32%（95±30） | ~8× | −1.59 ~ −1.76 | 稳定过 |
| `copresence_min` | ≈36%（55±20，周末 ×2.4） | ~10× | **−1.09 ~ −1.26** | **抖动** |

三个维的原始跌幅都很大，但 `copresence_min` 的 z 被三重压缩：

1. **自身方差大**：normalized 跌幅被 CV 36% 摊薄；
2. **残差 std 被双峰抬高**：`residual_stats` 是工作日/周末合池估计的
   （7 天留出段切不出两个池），而 copresence 有 2.4× 的周末效应；
3. **GRU 只看过去 7 天**：异常持续到第 3 天后输入窗填满异常日、预测跟着跌，
   残差进一步收缩。这是固定窗口预测器对**持续性**变化的固有钝感——
   与缺陷④是同一个"系统会习惯异常"的病，只是发生在模型层而非阈值层。

于是 z 恰好在 1.2 门槛两侧抖动（−1.26 过得了、−1.09 过不了），
"7 天窗内 5 天"永远凑不满。修复：`threshold_ratio` 1.2 → 1.0。
安全性由**结构**而非单维门槛提供（三项 AND + 5/7 持续性），
`TN_short_social`（社交低落仅 4 天）专门守这条线——降门槛后它仍保持安静，
确认没有拿误报换灵敏度。

> 这个缺陷的意义不在数值，而在**它是被"修好验证脚本"逼出来的**：
> 1.2 这个值曾"通过"端到端验证，只是因为当时 GRU 初值碰巧让 z 落在门槛之上。
> 不可复现的绿色掩盖了一个真实的灵敏度缺口。

### 7.3 长周期慢坡诊断（`--drift`）——一个否证 + 一个新发现

现有 9 个场景最长跨度 11 天，证明的是"能抓阶跃"。但老年抑郁的典型形态是
**数周到数月的缓慢退行**，这一段此前完全没测过。故加 4 个诊断场景
（默认不跑、不计分），终点幅度完全相同、只有到达时长不同，横向比较坡度效应。

**猜想（记为 A1）**：每周微调剔除"已判偏离的天"，但缓慢下滑每天都不够判偏离，
于是被当正常数据学进基线，形成正反馈——学进去 → 基线更低 → 下一步更难判偏离。
这是缺陷④⑥"系统会习惯异常"的同一族病，只是发生在**月度尺度的微调层**。

| 场景 | 首检延迟 | `sleep_efficiency` 的 z（首段→末段） | 偏离/异常天数 |
|------|---------|--------------------------------|--------------|
| DRIFT_30 | 9 天 | −1.28 → **−8.92** | 22 / 31 |
| DRIFT_60 | 10 天 | −2.35 → **−12.05** | 51 / 61 |
| DRIFT_90 | 29 天 | −1.67 → **−16.36** | 28 / 91 |
| PERM_step（对照） | 0 天 | −12.80 → −12.98 | 91 / 91 |

**A1 未复现**。四个场景的 z 全部随时间**增长**而非趋零，坡越缓只是首检越晚
（9→29 天），都能检出且不中途失效。已确认微调真的执行（两轨、early-stopping
触发、残差 alpha=0.3 合并、模型备份落盘），负结果不是静默失败造成的假象。
现有防线足够：scaler 建档后永久冻结、微调用低学习率 + early-stopping、
残差统计**指数加权合并而非替换**、一旦开始判偏离该天即被排除出微调集。

> 这是本项目第一个**有价值的否证**。它把"GRU 会不会把慢坡学成正常"从
> 猜测变成了有数据的结论，也说明当初"scaler 建档后不再重新拟合"这个设计
> 决策比看起来更重要——它是这条防线的地基。

**但对照组暴露了一个新问题：永久性变化会无限期每日报警。**

`PERM_step` 是为了区分"慢坡漏报"与"冻结满 14 天后正常重新基线化"才加的，
结果它自己成了发现：**连续 91 天每天都判 L3**，z 稳在 −12.9 完全不衰减。
逐日追踪冻结状态：

```
day40-52  冻结 True   ewma_n 停在 33   阈值 1.18   score 4.5   偏离
day54     max_freeze_days=14 触发，冻结释放
day56-72  冻结 False  ewma_n 35→51     阈值 1.91   score 4.5   仍偏离
```

冻结**按设计正常释放了**，阈值也确实回升（1.18→1.91），但 score 是 4.5——
重新基线化的速度远追不上。而 L3 的动作是短信 + 社区网格员 + 强制响铃，
且 `alert.py` / `daily_job.py` 里**没有任何冷却、去重或抑制机制**
（已 grep 确认无 cooldown / dedup / last_alert 相关实现），
所以 91 天就是 91 次完整预警。

这正是本文档反复强调的"比漏报更快摧毁信任"的失效模式：家属大概一周内
就会关掉系统。`max_freeze_days=14` 的注释写的是"该报的早已报过，重新基线化
是为了让系统对**下一次**变化仍然敏感"——设计意图对，但只释放了 EWMA 的更新，
没有解决"同一件事该报几次"。这是**预警策略层的缺口，不是检测层的 bug**：
检测是正确的（老人确实一直处于低效睡眠状态），问题在于把"状态持续"
当成了"每天都是新事件"。

> ⚠️ 幅度限定：这是合成数据上的大幅阶跃（z≈−13）。真实老人的衰退幅度可能
> 小得多，届时阈值追上的速度会快些。但"无抑制机制"是结构性的，与幅度无关。

---

> **这三个缺陷说明了验证的真正价值**：它们都不是"测试没写好"，而是真实的设计缺陷，
> 且**一层压一层**：
>
> - 缺陷④（EWMA 学会异常）让持续异常报不出来，顺带也掩盖了
>   缺陷⑤（好转同样报不出来）——修了④才暴露⑤；
> - 缺陷⑤修完后范围 2 看起来 9/9 圆满，但范围 1 的绿色本身是不可复现的；
>   补上 torch 种子才暴露缺陷⑥（`copresence_min` 的 z 在门槛上抖动）。
>
> 三者都是"系统会习惯异常"的同一族病：④在阈值层（EWMA 吃进异常日）、
> ⑥在模型层（GRU 固定窗口填满异常日）、⑤是方向信息在合成总分时被 abs 丢弃。
> 只跑范围 1（链路是否跑通）永远发现不了这一层；而**范围 1 自己不可复现时，
> 连它该发现的也发现不了**。
>
> 仍属层次 B，绝对数字（如 FPR）待真实数据校准，**不构成层次 C（真实有效性）证据。**

## 8. 代码走查（2026-07-31）：一组"验证够不到"的缺陷

### 8.1 为什么 312 全绿 + 19/19 + 9/9 之下还藏着这些

上一节的三个缺陷是**算法**没想对。这一节的一组则不同：算法基本是对的，
**断言打在了错的层**，于是缺陷在全绿的表象下长期存活。

| 断言在哪 | 实际该断言什么 |
|---------|--------------|
| `validate_synthetic.py` 数 `status == "cold_start_fallback"` 的天数 > 20 | 建档期的偏离**能不能出等级** |
| `test_camera_offline_degrades_social_only` 断言 `counts_toward_consecutive(track_quality)`（validator 的辅助函数） | **rules 层**是否真的跳过了那天 |
| `test_degraded_days_skipped_not_counted` 手搓带 `data_quality` 的字典 | 生产链路写出的日志**里到底有没有这个字段** |

三条都"通过"了，三条都没测到真正的缺口。这比测试没写更危险——它给出的是
**有保障的错觉**。

### 8.2 建档期 35 天完全没有预警能力

`cold_start_fallback.py` 存在的唯一理由是"消除 GRU 就绪前的监测盲区"。
它确实算出了偏离、给了带方向的 `signed_z`。但 `judge._judge_single_track`、
`rules._collect_signed_z`、`build_mpdd_evidence._quality` 三处状态白名单
只收 `("success","observation")`——兜底轨的结果**整个被丢掉**。

实测（新建 elder、无基线，第 20 天起注入严重睡眠恶化）：

```
 day date         注入异常  sleep.status          score  偏离   risk_level
  20 2026-03-21   ★是      cold_start_fallback  166.25  True   0 (正常)
  ...
  25 2026-03-26   ★是      cold_start_fallback   57.98  True   0 (正常)

检测层判偏离 6/6，预警层 risk_level>=1 的有 0/6
```

`daily_job` 只在 `risk_level >= 1` 时 `trigger_alert`，所以整个建档期
一条预警都发不出。**盲区在检测层补上了，预警层原封不动。**

修复后同一场景：`L1 → L1 → L2 → L2 → L3 → L3`（随连续天数逐级升）。

> 白名单此前以字面量散在五处，`cold_start_fallback` 只被加进了 `daily_job`
> 的两处。这类"多处各写各的"是同一个缺陷反复出现的温床，已抽成
> `src/utils/status.py` 单一事实来源。

### 8.3 只加白名单会立刻造出误报——两套尺度不可混用

兜底的 `anomaly_score` 是稳健加权 |z|，阈值就是 `fallback_sigma = 3.0`，
正常天实测跑到 **0.80 / 1.11 / 1.77**；而 GRU 轨是加权归一化残差，
正常 0.5~1.0、阈值 1.3~1.6。旧的绝对常数 `high_spike = 1.5` 对 GRU 轨是
"高峰"，对兜底轨是"再普通不过的一天"。

所以幅度门槛必须改成**倍数**：`severity = anomaly_score / 当日 dynamic_threshold`。
不管用哪套尺度，"越过自己的阈值多少倍"都表达同一件事。按定义 `severity > 1 ⟺ is_deviation`。

顺带修掉两个同源问题：

- **稀释**：`avg_anomaly` 算在整个 7 天窗，而方向闸门早已只看 streak，
  两个门槛看的不是同一段数据。实测 3 天各 1.45（都实打实越过各自阈值）
  被前面 4 个正常天拉到 0.907 < 1.0，只报 L1。
- **门槛必须 > 1**：改算 streak 后，偏离日按定义 `severity > 1`，
  旧值 1.0 等于恒真——"防止擦线偏离仅凭天数升到 L3"这条防线会**静默失效**。
  定为 `sustained_severity = 1.15`（整段平均要高出自己阈值 15%）。
  `high_spike_severity` 单独定 1.5：它作用在整个窗口含已恢复的日子，
  活着的偏离早被 `consecutive>=1` 判成 L1，峰值门槛唯一的职责是
  "已恢复但尖峰仍值得关注"，bar 理应更高。

### 8.4 "degraded 日跳过"在生产链路里从未生效

`validator` 判得对，但 `data_quality` 只写进 `features_{track}.csv`，
**没有随推理结果落进 `data/logs/daily_inference/*.json`**（实测 60/60 个
历史日志都没有该字段）。`rules._counts_toward_consecutive` 读不到就走
"旧日志无该字段，保守当作有效"分支恒返回 `True`。

于是 CLAUDE.md 里作为不变量写着的那句——"degraded/insufficient 的日子在
持续性统计中被跳过"——以及 `validator.py` 那段"否则传感器抖动会被攒成预警"
的设计理由，**都不成立**。

修复时改成**按轨**判定：质量本来就是按轨的，用单一顶层值会让睡眠轨降级
压住社交轨的持续性计数，等于在判定层把双轨的故障隔离又粘回去。

### 8.5 "连续 N 天"从不校验日历连续性

`load_daily_results` 取的是最近 N 个**文件**而非 N 个自然日；而两轨全不可用
那天 `daily_job` 直接跳过推理、**连日志都不生成**。两者叠加：

```
5 条日志跨越 22 个日历日（中间断 17 天） → consecutive=5 → L3（严重）
修复后                                   → consecutive=3 → L2
```

设备离线一段时间后，断裂两端的偏离日会被当成连续日拼起来。同源问题还包括
补算路径：`run_daily_pipeline --date 2026-07-01`（README 文档化的用法）
会拿"最新的 7 个日志"当那天的历史。

缺日与 degraded 走同一条路径（都是"这天我们不知道"），既不累加也不打断，
但连续跳过超过 `risk.continuity.max_skip_days`（默认 3）就打断——
否则一次长时间离线又会把两段无关的偏离粘起来。

### 8.6 7 天日志窗与 7 天门槛互卡

`circadian_disruption` 降级模式要求连续 7 天达标，而 `judge` 固定加载 7 条日志
（今天 + 6 天历史）。历史里只要有一个 degraded 日被跳过，计数上限就掉到 6：

```
历史含 0 个 degraded 天 → 连续 7/7 天, is_active=True
历史含 1 个 degraded 天 → 连续 6/7 天, is_active=False   ← 数学上不可达
```

而降级模式**正是因为睡眠轨不可用才进入的**，恰恰是最容易伴随数据质量问题
的场景——这条路径最脆的时候，正是它该起作用的时候。

这个缺陷此前被 8.4 掩盖着（字段从没落盘，所以从没跳过任何一天），
修好 8.4 之后它才会显形。**修一个缺陷会暴露下一个**，与 §7 的④→⑤→⑥同构。

### 8.7 周报：一份不会报错的假报告

`平均异常分 / 最高异常分` 两行取的是顶层 `r.get('anomaly_score', 0)`，
而双轨改造后分数只存在于 `r["sleep"] / r["social"]` 里。于是这两行**恒为 0.00**，
真实分数是 0.63~1.13。周报是家属实际会看的唯一产物，它把"一切正常"当成
事实报了出去，不报错、不告警。

给周轨补上入口后还立刻暴露两个从没被跑到过的缺陷：规则模板路径直接
`TypeError`（`**{f"{k}_trend": ...}` 把 `social_trend` 拼成 `social_trend_trend`），
以及本周无数据时静默拿别的周顶替——**标题写着这一周、正文却是另一周的数据**。

> 三者的共同形态与 §8.4 一致：**"测不到"被静默呈现成"有结论"**。
> 这是本项目反复强调、也反复重犯的失效模式。

### 8.8 结论

本轮不改任何算法思路，只把已有设计**真正接通**，以及把断言挪到正确的层。
验证状态：单测 312 → **332**，范围 1 19 → **20**（新增"兜底能出等级"断言，
实测抓到 2 个建档期兜底偏离日），范围 2 保持 **9/9**。

> 这一轮最该记住的不是任何一条具体缺陷，而是：**全绿不等于没问题，
> 要看绿的是什么。** 三条"通过"的断言分别测了状态流转、辅助函数、和手搓的
> 假数据，唯独没测真实链路的输出。

## 9. 第二轮走查（2026-07-31，集成 MPDD 抑郁通道时）：20 个缺陷

### 9.1 这一轮和上一轮是同一个病

§8 的结论是"全绿不等于没问题，要看绿的是什么"。这一轮开始时的状态是
**332 全绿 + 20/20 + 9/9**——也就是说，§8 修完之后新增的那些断言，同样没能
覆盖到下面这 20 项。共同特征还是**断言打在错的层**：

- 判级层（`judge`）与判型层（`rules`）对"这天算不算数"给出**不同答案**，
  而所有测试都只测其中一侧；
- `imputer` 的单测断言的是它自己写下的常量（`filled[1] == 0.0`），
  而不是这个常量流到下游会变成什么（−15σ）；
- 补算历史日这条路径**从来没有测试进过**，尽管 README 与 CLAUDE.md 都把它
  写成常规用法。

### 9.2 四个高危缺陷的实证

**① 补算历史日判成最新日**

`quick_judge` 调 `load_daily_results(n_days=N)`，取的是最近 N 个**文件**，
与传进来的 `day_key` 完全无关；`judge_risk_level` 随后把 `daily_results[-1]`
当成"今天"。

仓库当前状态即可复现：日志覆盖 2026-07-01~08-29，`required_history_days` = 25，
执行文档化的补算命令 `run_daily_pipeline.py --date 2026-08-15`：

| 应该 | 实际 |
|------|------|
| 基准日 08-15，窗口 08-09~08-15 | 基准日 **08-29**，窗口 08-23~08-29 |
| 按 08-15 的等级发预警 | 按 **08-29** 的等级发预警 |
| 契约 `risk_level` 来自 08-15 | 契约 `day_key`=08-15 但 `risk_level` 来自 08-29 |
| 08-15 写回 `risk_type_qualifies` | 写回守卫 `log_day == day_key` 不成立 → **永不写回** |

最后一行是最伤的：持续性链条在 08-15 留下一个永久空洞，之后任何跨过这天的
连续统计都会在这里断掉。

**② 单轨掉线不但没跳过，反而打断连续段**

`daily_job` 只把 `is_usable_for_inference` 的轨传给 `daily_inference`，
于是 `insufficient`/`offline` 的那一轨**既没有 `result[track]` 子字典、
也不在 `track_quality` 里**。`_counts_toward_consecutive` 的三级回退全部落空，
走到 `return True`，把这天当成"质量正常但不达标"→ **打断**。

设计要求是"跳过"（既不累加也不打断）。坏掉的恰恰是双轨架构**故障隔离**这条
存在理由本身：小贝壳掉线一天，本该只让睡眠轨那天不计数，实际却把攒了几天的
偏离段清零，`sleep_stability` 的连续 3 天门槛永远凑不满。

**③ 判级层完全不看 `data_quality`**

`_judge_single_track` 的 `usable` 只按 `is_evaluable(status)` 过滤，而 degraded 日的
`status` 是 `"success"`（`is_usable_for_inference` 放行 valid+degraded）。
于是它**既累加也能打断** `consecutive`，而 `consecutive` 正是驱动 L2/L3 的量。
`max_skip_days` 的语义在判级层也完全不存在。

| 场景 | rules（判型） | judge（判级） |
|------|--------------|--------------|
| 5 天社交偏离，其中 2 天 C6c 掉线判 degraded | 正确跳过 → 滚动窗只数到 3 < 5 → **不激活** ✔ | 5 天全数上 → consecutive=5 → **L3** ✘ |
| 真实 5 天睡眠恶化，第 3 天 degraded | 跳过 → 计数继续 ✔ | 第 3 天归零 → 只数到 2 → L3 永不到达 ✘ |

第一行是误报，而且落在代价最高的一级（L3 = 短信 + 强制响铃 + 社区网格员）；
又因为没有活跃风险类型，建议文案还会退化成通用的"连续5天异常，建议尽快联系老人"。
第二行是漏报。同一个缺陷两头都错。

修法是把日历回溯抽到 `src/utils/continuity.py:walk_back_days`，判级与判型共用
同一份实现——它们对"这天算不算数"必须给出同一个答案。

**④ imputer 在原始量纲填 0**

代码是 `filled[missing_mask] = 0.0`，注释写的是"归一化空间里 0 ≈ 训练均值，
是信息中性的占位"。但 `filled` 是**原始量纲**向量，会被原样写进
`features_{track}.csv`；归一化要等到推理层用冻结的 scaler 才发生。
论证在错误的空间里成立。

用 E001 自己的数据实测：

| 特征 | mean | std | 原始 0 归一化后 |
|------|------|-----|----------------|
| `night_hr_mean` | 61.68 | 4.06 | **z = −15.2** |
| `sleep_efficiency` | 0.859 | 0.073 | **z = −11.8** |
| `rar_amplitude` | 0.875 | 0.155 | **z = −5.6** |
| `deep_sleep_ratio` | 0.205 | 0.041 | **z = −5.0** |
| `copresence_min` | 69.9 | 48.6 | **z = −1.44** |

两个后果：

1. `copresence_min` 是 `social_decline` 权重最高的**必选维**，设计上"缺了它规则
   就永远不触发"（`validator.CRITICAL_FEATURES` 也是这个意思）。现在 z = −1.44
   足以让 `_exceeds(z, "down", 1.0)` 为真——**"测不到"变成了"确实没人来"**。
   `tests/test_integration.py` 里那条
   `test_social_contact_rule_cannot_fire_without_copresence` 是通过的，
   只因为它手搓了一个不含 copresence 的 `signed_z` 字典；生产链路填进去的
   是一个伪造值。这正是 §8.1 批评过的形态。
2. 缺 1 维时数据质量仍判 `valid`（`DEGRADED_THRESHOLD=2`），于是这一行 −15σ
   会进 `StandardScaler.fit` 与 GRU 训练集。scaler 一旦建档就**永久冻结**，
   之后所有 `signed_z` 的分母都是错的。

修法：填不上的维保持 `NaN`（这是本仓已有的词汇——`cold_start_fallback` 就用
`np.isnan` 判"这维今天测不到"并产出 `valid_features`/`skipped_features`）；
推理层用冻结 scaler 的均值补 GRU 输入（那才是真正的"归一化空间的 0"），
同时把该维**权重置零**排除出打分，并且不写进任何残差字典。

### 9.3 回归测试：先证明它们会红

新增 `tests/test_regression_2026_07_31.py`，14 条断言全部打在
`judge_risk_level` / `load_daily_results` / `impute_missing` / `trigger_alert`
这些真入口上，不打在辅助函数上。

**然后把六个被改动的文件回退到修复前的版本，重跑这个文件：**

```
13 failed, 1 passed
```

唯一通过的那条验证的是新增字段的一致性（旧代码里那个字段不存在，所以断言
恰好平凡成立）。其余 13 条确实抓住了缺陷。

这一步是刻意做的。§8 的教训是绿色本身不构成证据——**一条从来没红过的测试，
不能证明它在守着什么**。

### 9.4 修复后的验证状态

因为缺陷④改变了特征值语义，已冻结的 scaler / GRU / 残差统计全部作废，
按 `57c45bd` 的先例整体重建：重新生成 60 天模拟数据 → 重新建档
（sleep 504 参数 / social 405 参数，留出段 signed_std 0.9065 / 1.0382）
→ 重跑 60 天日志（60/60 success）。

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 单元测试 | 332 | **442** |
| 范围 1（链路正确性 + 双轨隔离） | 20/20 | **20/20** |
| 范围 2（判别力，10 场景） | 9/9 | **9/9** |

判别力未发生变化，说明这批修复没有以牺牲检出为代价——但也要如实说明：
现有场景都是**两轨数据齐全**的理想情况，缺陷②③恰恰只在"某轨降级/掉线"时
才显形，而**范围 2 没有这类场景**。这是当前验证覆盖的一个已知缺口，
新增的回归测试暂时顶着它。

> 这一轮最该记住的是：§8 修完之后，我们有了 332 个绿色的单测和两套端到端
> 验证，仍然漏掉了 20 个可构造出具体失败场景的缺陷。**验证覆盖的边界，
> 就是缺陷藏身的地方**——而边界通常不在"测得多不多"，在"测的是不是真实链路
> 会走的那条路"。

## 10. 预警按事件去重（2026-07-31，方案 B）

### 10.1 问题：把「状态持续」当成了「每天都是新事件」

§7.3 的 `PERM_step` 对照组暴露了这个缺口，但当时只做了记录。本节是它的收口。

`alert.py` 原本对每个 `risk_level >= 1` 的日子无条件调一次 `trigger_alert`，
而该函数**没有任何记忆**——不知道昨天发过没有，连"上次"这个概念都不存在。

实测（重建后的 E001 60 天数据 + `PERM_step` 场景）：

| | 修复前 | 真实事件数 |
|---|---|---|
| E001 60 天 `trigger_alert` 调用 | 22 次 | — |
| E001 60 天子女 App 推送（L2+） | **12 次** | **4 个** |
| E001 60 天强制响铃 + 网格员（L3） | **8 次** | 其中 2 个 |
| `PERM_step` 91 天（永久性衰退） | **91 次** | **1 个** |

三分之二是重复，而 E001 这份数据只注入了两段异常——温和情况尚且如此。

**后果不是"吵"，是系统最终变哑。** 家属关掉通知之后，真正的**新**变化也
收不到了。方向闸门（缺陷⑤）、幅度门槛（§8.3）、持续性统计（§8.4）——
前面所有为压低误报做的工作，在通知被关掉的那一刻全部失去出口。
这比漏报更快摧毁信任，而且不可逆：关掉的通知没人会主动再打开。

**检测层是对的。** 老人确实一直处于低效睡眠状态，每天判 L3 在事实层面没错。
错在通知层把"判定"与"通知"当成了同一件事。**判定要每天做，通知不该每天发。**
所以本轮修复没有碰 `judge.py` / `rules.py` 一行。

### 10.2 修复后

| | 修复前 | 修复后 | 压缩比 |
|---|---|---|---|
| E001 60 天 L2+ 推送 | 12 次 | **4 次** | 3.0× |
| E001 60 天 L3 强制响铃 | 8 次 | **2 次** | 4.0× |
| `PERM_step` 91 天 L3 | 91 次 | **4 次** | 22.8× |

E001 实际发出的 4 次通知：

```
2026-08-11  L2  escalated
2026-08-13  L3  escalated
2026-08-21  L2  escalated
2026-08-23  L3  escalated
```

**恰好对应修复前统计出的 4 个真实事件**，一个不多一个不少。

`PERM_step` 的 4 次是「开始 1 次 + 月度重提 3 次」（`level_3.repeat_days: 30`）。
L3 会惊动社区网格员，完全静默不合适；月度重提是"不骚扰"与"别被遗忘"之间的折中。

`transition` 分布（E001 60 天）：
`{none: 31, cooldown: 15, escalated: 4, improved: 2, started: 1}`

### 10.3 最关键的一条不变量：升级穿透一切抑制

纯粹按"同一等级 X 天内最多一次"做冷却，会出现这种情况：

```
D1  L2 → 发通知，进入 7 天冷却
D3  L2 → 冷却中，不发   ✓ 对
D5  L3 → 冷却中，不发   ✗ 恶化被冷却窗吃掉
```

**这是拿误报换漏报，比完全没有冷却更危险。** 所以 `alert_state.decide()` 把
升级判定排在**所有**抑制判据之前，且无视 `acknowledged`。

实现时确实踩到了这个坑：初版把"同日幂等"（补算/重跑同一天不重复通知）
排在了升级判定之前，结果同一天重算出更高等级会被静默。**这个错误是被
`test_integration.py` 一条既有用例抓出来的**——那条用例在同一个测试函数里
先发 L1 再发 L2，恰好构成"同日升级"。

> 这是一次意料之外的收益：一条为别的目的写的集成测试，抓住了新代码里
> 最危险的那类错误。它也说明为什么断言要打在真实入口上——如果那条用例
> 测的是 `decide()` 而不是 `trigger_alert()`，就不会覆盖到调用顺序。

`tests/test_alert_events.py` 的 `TestEscalationBypassesEverything` 是这条防线的
专职守门员，三条用例分别守：冷却期内升级、已确认后升级、同日重算出更高等级。

### 10.4 配套的告知义务：周报回执

通知层静默后，如果周报也一字不提，"系统安静"与"系统挂了"就无法区分——
这与本仓「长期降级和长期正常必须可区分」（`check_prolonged_degradation`
存在的理由）是同一条原则。

所以新增了「预警回执」章节：持续中的事件每周在周报里露一次面，
低强度、不推送、不响铃，并明确写出"**静默不代表已缓解**"。
`_empty_report` 也带上——无数据周恰恰最需要它：设备掉线导致本周没有判定，
但上一个事件可能还开着，静默 + 空周报 = 两层遮蔽。

### 10.5 测试隔离：一个差点制造"不可复现的绿色"的坑

`trigger_alert` 现在是**有状态**的，把事件状态落到
`data/logs/alert_state/{elder_id}.json`。而 `tests/conftest.py` 当时只有 10 行，
没有任何数据目录隔离。不处理的话有两个后果：

1. 跑一次 pytest 就往**真实数据目录**写状态，污染 E001 的生产数据；
2. 状态**跨 pytest 会话残留**——第一次跑是"首次通知"，第二次跑同一条用例
   就变成"冷却中"，**测试结果取决于跑过几次**。

第 2 条正是本仓最忌讳的形态：不可复现的绿色（§7 开头记过，曾因未固定 torch
种子给出假的 19/19）。解法是 conftest 里的 autouse fixture，把
`alert_state.get_alert_state_dir` 重定向到 `tmp_path`。

顺带：写新测试时自己造了一条**假通过**的断言——
`assert r["transition"] != TRANSITION_NEW_TYPE`，而这条在事件被判成 `started`
时同样成立，测不到本意。已改为断言确切的 `cooldown`。

> 本节的教训与 §8、§9 一脉相承：**绿色本身不构成证据**。这一轮的绿色里，
> 有一条是靠"跑第一次"才成立的，有一条是靠"断言太宽"才成立的。
> 两条都不是代码错了，是**测试没测到它声称在测的东西**。
